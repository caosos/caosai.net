# Public Discoverability and SEO Contract

## Purpose

CAOS will include app-gated capabilities, but the platform still needs public crawlable pages so search engines, users, customers, partners, and future integrators can understand what CAOS is before logging in.

Public discoverability is part of the launch plan.

## Core rule

App-gated features need public descriptive pages. Search engines cannot understand private authenticated UI unless CAOS provides public crawlable explanations of the product, features, verticals, and use cases.

## Required public page categories

Public launch surfaces should eventually include:

- home / landing page
- about CAOS
- about the system designer / safe biography
- features overview
- memory and continuity page
- receipts and transparency page
- provider/model choice page
- connectors/tools page
- CAOS Care overview
- CAOS Connect overview
- CAOS Trading overview if retained
- machine/process guidance vision page
- pricing or access model page when ready
- privacy page
- terms/safety page
- changelog or roadmap page if appropriate

## Public vs authenticated separation

Public pages may describe capabilities, but must not expose:

- private user memory
- thread content
- files/photos/artifacts
- support tickets
- connector data
- admin diagnostics
- private receipts
- secrets or environment details

Authenticated app surfaces remain gated. Public pages explain what exists and why it matters.

## Search engine requirements

The public site should eventually include:

- crawlable HTML content
- meaningful page titles
- meta descriptions
- canonical URLs
- Open Graph tags
- basic Twitter/X card metadata if useful
- sitemap.xml
- robots.txt
- Schema.org JSON-LD where appropriate
- accessible headings and semantic structure
- fast-loading pages
- non-JavaScript fallback content for core descriptions where practical

## Feature page rule

Each major app-gated feature should have a public descriptive page or section explaining:

- what it is
- who it helps
- what problem it solves
- what data it may use
- what is private/gated
- what receipts or user controls exist
- what safety boundaries apply

## Domain strategy

Known ecosystem domains:

- `caosos.com` — core platform
- `caoscare.com` — care/senior-care vertical
- `caostradings.com` — trading/finance vertical concept
- `caosconnect.com` — connector/integration vertical

Each domain should have public discoverability appropriate to its vertical while sharing the same privacy, receipts, and trust doctrine.

## Content doctrine

Public CAOS pages should be direct, accurate, and plain-language. Do not overclaim. Do not imply autonomous high-risk action without explaining gates and receipts.

Claims must distinguish:

- live features
- planned features
- experimental features
- long-term vision

## Launch acceptance criteria

Before public launch, CAOS should have:

- public crawlable landing page
- public feature overview
- privacy page
- basic sitemap.xml
- robots.txt
- metadata/canonical strategy
- app/login separation
- no private app data exposed publicly

## Non-negotiable

A login-gated app without public explanatory pages is not discoverable. CAOS must have public crawlable pages that describe the platform without exposing private user data.
